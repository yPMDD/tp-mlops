TP 7 — Automatiser les workflows MLOps
Durée : 3 h · Partie 5 du cours · Windows PowerShell




Un pipeline qu'il faut lancer à la main n'est pas automatisé. Ce TP transforme le pipeline du TP 4 en workflow planifié,
surveillé depuis une interface web, capable de se déclencher tout seul, de s'arrêter sur une règle de qualité et de notifier
l'équipe. Deux outils open source, tous deux présentés dans la partie 5 du cours et utilisés entièrement en local : Prefect
pour l'orchestration (workflow écrit en Python, piloté depuis une interface web), et Node-RED pour l'automatisation
low-code (flux construits à la souris) : un bouton qui relance le réentraînement, et une surveillance du modèle en service
qui alerte quand il tombe en panne.

     VERSION WINDOWS
     Toutes les commandes sont écrites pour Windows PowerShell (5.1 ou 7), jamais l'invite cmd.exe. Les blocs @' ... '@
     écrivent un fichier ou l'envoient à Python : le marqueur de fermeture '@ doit être en tout début de ligne, et le bloc se colle
     en entier. Les fichiers sont écrits en -Encoding ascii : l'encodage UTF8 de PowerShell 5.1 ajoute un marqueur
     invisible en tête de fichier qui casse la lecture des fichiers YAML et JSON.
     Si l'activation de l'environnement est refusée : Set-ExecutionPolicy -Scope Process -ExecutionPolicy
     RemoteSigned, puis relancez .venv\Scripts\Activate.ps1.


     CE QUI CHANGE DANS CETTE VERSION
     La chaîne GitHub Actions (qui exigeait un compte GitHub et des données accessibles en ligne) est remplacée par
     Node-RED, l'outil d'automatisation visuelle open source de la partie 5 : tout se fait sur votre poste. Les étapes 1 à 5
     (Prefect) ne changent pas. Toutes les sorties ont été obtenues réellement avec Prefect 3.9.0, Node-RED 5.0.9 et MLflow
     3.17.2 ; les captures de Node-RED viennent de cette exécution.




Objectifs pédagogiques
 •    Transformer un script en workflow composé de tâches observables
 •    Piloter et surveiller les exécutions depuis une interface web
 •    Planifier un déclenchement périodique sans intervention humaine
 •    Interrompre automatiquement le workflow sur une règle de qualité
 •    Construire sans code un flux qui déclenche le workflow et surveille le modèle en service
 •    Versionner un flux low-code comme du code


Prérequis
 • TP 4 terminé : le pipeline DVC fonctionne (dvc repro)
 • TP 6 terminé : le modèle fraude-flaml est dans le registre MLflow avec l'alias production
 • Node.js 18 ou plus récent (nodejs.org, version LTS) pour Node-RED


Installation
Prefect fournit un serveur local avec interface web, sans base de données à installer. Node-RED s'installe avec npm, le
gestionnaire de paquets de Node.js.
terminal

  cd tp-mlops; .venv\Scripts\Activate.ps1
  pip install prefect
  prefect version
  node --version                                       # 18 ou plus
  npm install -g node-red

Étape 2 — Écrire le workflow
Chaque étape devient une tâche observable, avec ses réessais. Le workflow appelle le pipeline DVC existant : on n'a
rien réécrit. Vérifiez d'abord que les paramètres sont bien ceux de référence.
terminal 2

  Select-String -Path params.yaml -Pattern 'n_estimators|max_depth'


  RÉSULTAT ATTENDU

    max_depth: 12

  Si vous lisez 600 et 20, ce sont les reglages du dernier dvc exp run du TP 4 :
  remettez 300 et 12 dans params.yaml avant de continuer.


flow_mlops.py

  @'
  import json, subprocess, yaml
  from prefect import flow, task, get_run_logger
  @task(retries=2, retry_delay_seconds=10)           # 2 reessais en cas d'echec
  def rejouer_pipeline():
      r = subprocess.run(['dvc', 'repro'], capture_output=True, text=True)
      get_run_logger().info(r.stdout[-800:])
      if r.returncode != 0:
          raise RuntimeError(r.stderr[-500:])
      return 'pipeline rejoue'
  @task
  def lire_metriques():
      return json.load(open('reports/metrics.json'))
  @task

Étape 6 — Installer et démarrer Node-RED (10 min)
Node-RED est un outil d'automatisation visuelle open source (licence Apache 2.0, fondation OpenJS). On y construit des
flux en reliant des nœuds : un nœud reçoit un message (msg), le transforme, et le passe au suivant. Le contenu utile du
message est dans msg.payload. Rien ne s'exécute tant que le flux n'est pas déployé (bouton rouge Deploy en haut à
droite).
terminal 4 : Node-RED

  cd tp-mlops
  node-red


  RÉSULTAT ATTENDU
  Welcome to Node-RED
  ...
  [info] Server now running at http://127.0.0.1:1880/
  [info] Started flows


  1. Ouvrez http://127.0.0.1:1880 dans le navigateur. Fermez la visite guidée et répondez No, do not enable
      notifications à la question sur les mises à jour.
  2. Repérez les zones : à gauche la palette (les nœuds rangés par catégorie : common, function, network, storage...), au
      centre l'espace de travail avec ses onglets de flux, à droite la barre latérale. Ouvrez l'onglet Debug de la barre
      latérale (icône d'insecte) : c'est là que s'afficheront les messages.
  3. Renommez l'onglet Flow 1 (double-clic sur l'onglet) en Réentraîner d'un clic.
Si ça coince : si PowerShell refuse d'exécuter node-red (script non signé), lancez node-red.cmd, ou autorisez les scripts
pour la session avec la commande Set-ExecutionPolicy donnée en tête de fiche.

Étape 8 — Flux 2 : surveiller le modèle en service (25 min)
Toutes les 10 secondes, Node-RED envoie une transaction au modèle FLAML du TP 6, affiche une alerte si le modèle
prédit une fraude, et surtout détecte la panne du service lui-même : il écrit alors un incident horodaté dans
reports/alertes.log. Créez un nouvel onglet (bouton + au-dessus de l'espace de travail) nommé Surveiller le
modèle. Démarrez d'abord le point de terminaison :
terminal 5 : le modèle en service

  cd tp-mlops; .venv\Scripts\Activate.ps1
  $env:MLFLOW_TRACKING_URI = "http://127.0.0.1:5000"
  mlflow models serve -m 'models:/fraude-flaml@production' -p 8101 --env-manager local

  1. inject nommé Toutes les 10 s : msg.payload de type {} JSON avec la valeur
      {"dataframe_records":[{"montant":8500.0,"anciennete":3,"freq_24h":9,"nuit":1}]} ; en bas
      de la fenêtre, Repeat = interval, every 10 seconds.
  2. http request nommé Modèle : /invocations : POST, URL http://127.0.0.1:8101/invocations,
      Return = a parsed JSON object.

  POURQUOI LA RÈGLE 2 DU SWITCH EST « == 0 » ET NON « otherwise »
  Lors de la préparation, le switch avait une règle « otherwise ». Quand le service est tombé, le nœud http request a aussi
  transmis un message contenant le texte de l'erreur : il est parti dans « otherwise » et s'est affiché comme... « Transaction
  normale ». Une surveillance qui classe une panne en cas normal est pire que pas de surveillance : testez toujours le cas
  de panne.



Étape 9 — Versionner le flux low-code et conclure (15 min)
Un flux construit à la souris n'existe que dans Node-RED tant qu'il n'est pas exporté. On l'exporte en JSON et on le
commite à côté du code, comme le workflow Orange au TP 5.
  1. Menu principal (les trois traits en haut à droite) > Export > all flows > Download : enregistrez le fichier dans
      tp-mlops/nodered/flows.json.
  2. Ouvrez ce fichier dans un éditeur de texte : chaque nœud est un objet JSON avec son type, son nom, ses réglages et
      ses liens (wires). Retrouvez l'URL de Prefect et le seuil du switch.
terminal 2

  git add flow_mlops.py nodered/flows.json
  git commit -m 'auto: workflow Prefect et flux Node-RED'

Rédigez enfin dans reports/tp7_synthese.md un tableau comparant Prefect et Node-RED sur : ce qui déclenche
l'exécution, qui peut la modifier, ce qui se passe en cas d'échec, comment on la versionne, et le type de tâche pour
lequel chacun est adapté. Ajoutez une ligne pour une chaîne d'intégration continue (GitHub Actions, GitLab CI), vue en
cours sans être pratiquée ici.
